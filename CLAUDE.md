# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project priorities

1. **Absolute minimum RAM use.** Pindrel must run on weak devices (an old Raspberry Pi, an old phone). Target: **hard ceiling of 512 MB RAM**, **recommended 256 MB**, counting everything needed to run, database included. The limit applies **per instance**; behind a load balancer each API instance follows the same individual ceiling. In practice: prefer small dependencies, don't hold whole datasets in memory, cap connections and memory spikes (e.g. key derivation). Judge every new dependency against this. **RAM is the resource that matters most; storage (disk, binary and install size) has a much lower priority.** Spending storage is acceptable when it lowers RAM use or removes a bug (for example a dependency or a native plugin that replaces a polling loop, an on-disk cache instead of an in-memory one). When a change is justified by RAM, measure it before and after instead of assuming.
2. **Cost split between client and server.** Neither side should absorb all the overhead for the other. Where overhead is unavoidable (security, cryptography) it takes priority, but balanced between the parties.

## Project

Pindrel is a self-hosted, Notion-style notes workspace (AGPL-3.0). Three clients-of-one-API and a gateway live in this monorepo:

- `backend/` — Go API (Go module name is `pindrel`, so imports look like `pindrel/internal/auth`)
- `gateway/` — Rust (the only Rust in the project): the front-facing process of a deployment. Load balancer over the API replicas, per-IP rate limits (`governor` for the GCRA math and clock, our own client table capped at 16 384 entries per limit, `Retry-After` on every 429), mDNS announcement and LAN discovery (`GET /server/discover/`). Static binary of ~1.4 MB, ~2-5 MB of RAM; runs natively on Linux (x86/arm), Windows and macOS (only `cargo check` was run for the non-Linux targets) or as a `scratch` Docker image of ~2.5 MB. Nothing in the Go API depends on it.
- `web/` — Svelte 5 + Vite + Tailwind SPA (Yarn Berry with PnP SDKs in `web/.yarn`)
- `mobile/` — Flutter app (mobile + desktop), Flutter version pinned via FVM (`mobile/.fvmrc`)
- `shared/protos/` — Protobuf schema shared by all three

Only the auth routes are implemented so far. Notes, vault and bulk sync are planned.

**Client/server roles:** the Go API exists for authentication, cloud storage and sync. `mobile/` is fully self-sufficient (local storage, works without any server; the API is optional). `web/` ships embedded in the API image and depends on it for login, but is semi-self-sufficient: notes are kept in the browser's IndexedDB (`idb`). Both login screens will have a top tab to add another server: web **always defaults to the embedded server** (other servers found via mDNS are extra options; browsers cannot do mDNS, so the embedded backend does the discovery and hands the list to the web), mobile lists the servers found on the current network and picks none on its own (the person chooses; a server never opened before is paired first, see "Pairing by six digits"). mDNS (`_pindrel._tcp`) advertises the front-facing service, i.e. the gateway, never each API instance. The gateway side is implemented (see Gateway); the web and mobile login tabs are not.

**The API must be explicitly stateless** so it can run behind a load balancer: no session/cache/counter state in process memory; state lives in Postgres or the JWT; `JWT_SECRET` is shared across instances. The in-memory login/register limiters and the global `httprate` limit are per instance, so they are behind `IN_APP_RATE_LIMIT` (default `true`, for the single-instance setup); with the gateway overlay it is `false` and the gateway does the limiting instead.

## Commands

### Backend (run from `backend/`)

```bash
cp .env.example .env            # config.Load() fails if any required var is missing
go run ./cmd/api                # needs a reachable Postgres
go test ./...                   # integration tests: need Postgres + backend/.env
go test ./internal/auth -run TestDB_Service_Register_DuplicateEmail -v   # run a single test
sqlc generate                   # regenerate internal/database/db from queries/ + migrations/
swag init -g cmd/api/main.go    # regenerate docs/ (Swagger) from handler annotations
```

Tests are not unit tests with mocks. `setup_test.go` files load `../../.env` (i.e. `backend/.env`) and connect to the real database. They create dummy users and delete them in `t.Cleanup`. Start Postgres first, for example with `docker compose up postgres`, which exposes port 5432.

Migrations in `internal/database/migrations` are run by **golang-migrate** (`NNNNNN_name.up/down.sql`): the CLI by hand (`migrate -path internal/database/migrations -database "$URL" up|down|force N`, what the CI also uses against a throwaway Postgres) and the library inside the API, which applies the files embedded in the binary at startup (`database.Migrate`, `internal/database/migrate.go`; Postgres advisory lock, so replicas starting together do not race; same `schema_migrations` table as the CLI). Rules: **every migration file is ONE implicit transaction** (no `BEGIN`/`COMMIT`, nothing Postgres refuses inside a transaction such as `CREATE INDEX CONCURRENTLY`; `TestMigrationsAreAtomic` enforces it). golang-migrate marks the database *dirty* while a file runs and leaves it dirty if the file fails, which would stop every later start (even the previous release the deploy rolls back to); because a failed file changed nothing, `MigrateFS` moves the version back to the one before it and runs again. Migrations only go forward and the automatic rollback of a bad release (`deploy/update.sh`) does not undo applied ones: write destructive changes in two releases. A database migrated by hand (without `schema_migrations`) is adopted with `migrate ... force <last applied version>`. The tests (`TestDB_Migrate_*`) migrate throwaway schemas of the real database, so apply the migrations by running the API once (or the CLI) before running the other tests.

### Gateway (run from `gateway/`)

```bash
cargo test                     # unit + integration (fake replicas) + binary + mDNS; mDNS tests say so and pass without multicast
cargo fmt --check && cargo clippy --all-targets -- -D warnings
cargo build --release          # target/release/gateway
cargo audit --deny warnings && cargo deny check   # advisories, licenses (deny.toml), sources; also in the gateway CI (the ci-pc image has both)
cargo +nightly fuzz run client_ip fuzz/corpus/client_ip fuzz/seeds/client_ip   # mkdir -p fuzz/corpus/client_ip first (libFuzzer writes what it finds into the FIRST directory, so the committed seeds go second); also discovered_servers, settings; needs nightly + cargo-fuzz (in ci-pc); the CI runs each for 40 s
# 64-bit Raspberry Pi from another machine, no C toolchain (gateway/.cargo/config.toml sets rust-lld + crt-static + pic;
# without them the binary linked this way segfaulted at startup on a real Pi 4):
rustup target add aarch64-unknown-linux-musl && cargo build --release --target aarch64-unknown-linux-musl
UPSTREAMS=127.0.0.1:9101-9110 GATEWAY_PORT=8200 SERVER_NAME=Casa cargo run --release
```

Environment: `UPSTREAMS` (required, `ip:port[-port]` list, e.g. `127.0.0.1:9000-9099,10.0.0.5:8080`), `GATEWAY_PORT` (8080), `SERVER_NAME` (Pindrel), `TRUSTED_PROXIES` (empty) and `CLIENT_IP_HEADER` (`x-forwarded-for`: behind Cloudflare Tunnel / `tailscale serve` set `TRUSTED_PROXIES=127.0.0.1,::1` and, for Cloudflare, `CLIENT_IP_HEADER=cf-connecting-ip`; only that one header is read, only from those peers, right to left; see `gateway/src/clientip.rs`), `MDNS_ENABLED` (true), `MDNS_INTERFACES`, `MDNS_REFRESH_SECS` (15; 0 = off), `KNOWN_PROBE_SECS` (15; 0 = off), `KNOWN_SERVERS_FILE` (unset = memory only), `SERVER_ID_FILE` (unset = a new id on every start), `RATE_LIMIT_ENABLED` (true), `PROBE_INTERVAL_SECS` (3), `MAX_CONNECTIONS` (1024), `MAX_CONNECTIONS_PER_IP` (64; one client cannot hold every slot with silent sockets; declared proxies are exempt, their clients are limited per request), `MAX_BODY_BYTES` (1 MiB). The gateway protobuf (`ErrorHttp`, `DiscoveredServers`) is encoded by hand; `gateway/tests/golden/*.bin` are generated with `protoc --encode` and decoded by both the Rust tests and `backend/internal/api/golden_test.go`, and a test checks the field numbers against `shared/protos`. After changing `server.proto`/`auth.proto` regenerate them. Behaviour to keep: `GET /server/discover/` is the map of the LAN, so it answers 404 to requests that came through a `TRUSTED_PROXIES` proxy (a tunnel); the LAN is found with `netdev` (up, not loopback, not a tunnel/point-to-point such as Tailscale, private IPv4; the default route and physical interfaces break ties), announced addresses outside that subnet are dropped from the list, the list handed out is capped at 64 servers with names/hosts at 64 chars and 8 addresses (the web throws away an answer over 64 KiB, so a flood of announcements must not be able to blank the list), and `x-pindrel-address` uses the same address; the gateway is the edge, so it replaces any client `X-Forwarded-For`; a failed *connection* is retried on the next replica even for POST (the replica never saw it), a timeout is not (504); a connection that closes *after* the request was written (a replica being stopped by a rolling update) is replayed on one other replica only for GET/HEAD/OPTIONS (anything else may have been processed, so the client gets a 502), and only once so a request that kills replicas cannot walk through all of them; `GET /server/info/` through the gateway gets an `x-pindrel-address: <lan ip>:<port>` header (the address the LAN uses; never sent when the request came through a `TRUSTED_PROXIES` proxy, since that client may be on the internet), which the web shows instead of the host it was opened by (`localhost`, a VPN address); `GET /server/info/` also carries `Access-Control-Allow-Origin: *` + `Access-Control-Expose-Headers: x-pindrel-id` (public, read-only; the web uses it to validate typed-in servers); WebSocket (`/ws/sync` is planned) goes through as an HTTP/1.1 `Upgrade` that the gateway joins byte for byte to a replica (`src/websocket.rs`: 4 KiB per direction, `MAX_WEBSOCKETS` 1024 and `MAX_WEBSOCKETS_PER_IP` 32 because a tunnel outlives the HTTP connection that the connection limits count, `WS_IDLE_SECS` 600, tunnels are closed on shutdown; WebSocket over HTTP/2 is refused with 426, no browser offers it). Docker starts containers with a soft limit of 1024 open files and a tunnel takes two: `compose.lb.yml` raises it to 8192 and the gateway warns at start when the limit is too low for its own settings. HTTPS is optional and built in (cargo features `tls`, `selfcert`; the image has `selfcert` by default and `compose.tls.yml` turns it on, see "TLS" below).

**Release tags (rules).** A release exists only because someone created a `v*` tag; nothing in Forgejo creates tags on its own.
- Format `vMAJOR.MINOR.PATCH` (`v1.2.0`); a dash makes a pre-release (`v1.2.0-rc1`: no `1.2` Docker tag, marked pre-release).
- Tag the commit on `main` that `release-images.yml` already published images for (its `version-tags` job on GitHub fails with a clear message when the commit has no image); a tag on `dev` is only for testing the other jobs.
- Never move, delete or reuse a tag that was published: the Docker version tags and installed apps depend on it (the Android `versionCode` is the commit count, which must only grow). Fix a bad release with the next patch version.
- A failed run leaves an invisible draft release: re-run (uploads replace by name) or delete the draft. Delete test releases and their tags once done.
- **Claude must not create or push tags (or releases) unless the user asks for it explicitly in that moment**: it publishes files and Docker tags outside the repository.

`docker compose -f compose.yml -f compose.lb.yml up -d --build --scale pindrel=2` adds the Rust `gateway` (`gateway/Dockerfile`, multi-stage to a `scratch` image, 48m cap (a flood of 1500 idle sockets peaked at 31 MiB), host network, healthcheck `/gateway healthcheck`) in front of the replicas, which stop publishing on the network and publish only on `127.0.0.1:9000-9099` (one port per replica, up to 100; widen both ranges for more) because the host network has no docker DNS. The replicas then run with `IN_APP_RATE_LIMIT=false` (the gateway limits). Measured with 2 replicas: gateway container 0.9 MiB (cgroup) / 1.8 MB RSS, API 43-63 MiB each (peaks after Argon2 logins), Postgres ~24 MiB. The real replica limit is Postgres (`max_connections=20`: with `DB_MAX_CONNS` pools, ~8 replicas at the default; more needs a smaller pool or PgBouncer). A plain `docker compose up` has no gateway and therefore no mDNS.

`docker compose up --build` builds one image (the `Dockerfile` builds both `web/` and the Go server) and runs it with `postgres:18-alpine`. The final image is a stripped static Go binary on Alpine, run as non-root with `GOMEMLIMIT=64MiB` (measured: 100 MiB let the Go collector keep ~120 MiB of mostly garbage at the peak, 64 MiB cut the peak to ~76 MiB at the same throughput; 48 MiB went to ~63 MiB but gave more `503 server_busy` under 300 simultaneous devices; keep it above the ~53 MiB live peak of two Argon2 runs) and a `wget` healthcheck on `/`. The container always listens on 8080; compose's `PORT` only picks the host port. Compose reads `backend/.env` when present (optional) and also sets defaults inline. It enforces the RAM budget: `mem_limit` 128m for `pindrel` + 128m for `postgres` (= the recommended 256 MB), `GOMEMLIMIT=64MiB`, small Postgres buffers, and Postgres published on loopback only.


### TLS (decided design, option 4: the gateway is its own CA)

- **Why:** the native apps need HTTPS (release Android and iOS refuse plain HTTP; secure contexts also unlock service workers, `crypto.subtle`, clipboard in the web). A LAN has no domain, so the gateway keeps its own certificate authority: `TLS_AUTO=true` + `TLS_DIR=/data/tls` (the `gateway-data` volume: **keep it**, a lost CA means every paired device pairs again). `TLS_PORT` (compose: 8443) serves HTTP/1.1 and HTTP/2 (TCP only; HTTP/3 was built and measured, then removed on purpose: +0.6 MiB of RAM and a lot of code for a gain only on bad networks, see `tools/https-bench/RESULTADOS.md`). Env: `TLS_SANS` (extra names), `TLS_REFRESH_SECS` (3600; the certificate is looked at again, renewed files and changed addresses take effect with no restart, a broken renewal keeps the old certificate), `HTTP_MODE` (`full` default, or `redirect`), `WS_ALLOWED_ORIGINS`, `MAX_WEBSOCKETS` (1024), `MAX_WEBSOCKETS_PER_IP` (32), `WS_IDLE_SECS` (600). `TLS_CERT_FILE`/`TLS_KEY_FILE` instead of `TLS_AUTO` serve a certificate somebody else manages (lego, certbot, a tunnel).
- **The CA** (`src/selfcert.rs`): EC P-256, 10 years, **name-constrained to DNS names of the local network** (`localhost`, `.local`, `.lan`, `.home.arpa`, the machine's name, the names given when it was created; IPs are not constrained because the BoringSSL inside Dart refuses a CA with IP constraints). A name added later that the CA cannot vouch for is left out of the certificate with a log warning. The server certificate lasts 1 year and is renewed 30 days before the end or when the machine's addresses change. `ca.key` and `server.key` are 0600.
- **Pairing:** `GET /server/ca.pem` (and `/server/ca.crt` as a download) serve the public CA; `x-pindrel-ca` on `/server/info/` is its SHA-256 and `x-pindrel-tls` the TLS port. The pairing code is `pindrel://pair?host=ip:port&ca=<sha256>&n=<name>` (printed at start, shown as a QR code on `/server/connect/`). The printed and displayed **confirmation code** (`3DC3-39F4-232A`, the first 48 bits of the fingerprint) is what a person compares between the page, the gateway log and the app; the code carries the whole fingerprint, which is what the app checks. A native client downloads the CA and keeps it **only if its SHA-256 equals the code** (`mobile/lib/core/network/pairing.dart`), then trusts that CA for that server and nothing else (`SecurityContext(withTrustedRoots: false)`). The camera scan and the "add server" screen of the app are not built yet; the pairing logic and its tests are.
- **Pairing (`gateway/src/pairing.rs`, `mobile/lib/core/network/pairing.dart`)**: mDNS proves nothing, so a person vouches for the server once. Two ways, both over HTTPS from the app (`/server/pair/*`, LAN peers only, never through a declared proxy):
  - **By six digits, in a room.** A person at a page of the server (the connection page, or the "Parear um aparelho" box of the web login) asks for a **room** (`POST /server/pair/room`, any scheme): a 4-digit code and a secret token that stays in that page's memory and goes in the `x-pindrel-room` header (never a URL). The code is typed into the app, which starts a session in that room: it commits to a random number (`POST /server/pair/start` with `c=sha256(a)` and `room=`), gets the server's number, reveals its own (`/server/pair/reveal`), and both sides compute `sha256("pindrel-sas-v1" || CA fingerprint || a || s)` as six digits; the app shows its digits and **only the page that holds the room's token** (`GET /server/pair/room`) shows the server's; the person compares and the app keeps the CA only on "same" (`POST /server/pair/done`: 204 = that session was still the live one, 409 = replaced or expired, and the app pairs only on 204). Fresh committed numbers mean somebody in between with another CA gets other digits (1 in a million a try) and cannot grind for a match. The room code only routes: guessing it gets a session whose digits the rightful page shows and the person refuses; wrong codes lock an address after 3 tries for 5 min. Up to `PAIRING_MAX_ROOMS` (6) rooms are open at once, each with its own digits, a room lasts 3 min and one phone, and the digits renew every 60 s (the app asks again by itself, same room, until the room ends). The log also prints each session's digits.
  - **With the master code (80 bits, `XXXX-XXXX-XXXX-XXXX`, Crockford base32).** For whoever has the host and no page to open. The gateway prints it in its log (`PAIR: código mestre ...`) and nowhere else. The app and the server prove to each other that they know it without sending it: `HMAC-SHA256(master, "pindrel-master-a"|"-s" || CA fingerprint || a || s)`, checked in constant time, mutual (the app verifies the server's proof too), so nobody in between with another CA can pass and 80 bits cannot be searched from a watched proof; nothing to compare. There is exactly **one** code (no setting for more: each extra one would be another secret in the log). It works once, for 24 h at most, and is replaced (and the new one printed) after it is used, when it expires (a clock checks every minute) and after 5 wrong proofs from anyone; 3 wrong tries lock an address. How many people may pair at once is the number of rooms, `PAIRING_MAX_ROOMS` (default 6, 1 to 64). Both languages check the same vectors (`master 1..10` = `0410-6105-0R3G-G28A`).
  - In the app: `PairingDialog` (a server on the network: room code first, "Tenho o código mestre" as the alternative) and `AddServerDialog` (address, optional name, the room code and the six digits as required fields, or the master code); `dart run tool/pair_digits.dart host:port --room 1234 [--view-token T]` or `--master CODE` plays it from the command line. The QR / `pindrel://` code stays as a third way.
- **The connection page** (`src/connect.rs`, written to reassure, not to look like a phishing page): it opens with "this is a server of your network" (machine name and address), says what it does and does not do (asks no password, sends nothing out, loads nothing from outside: enforced by its CSP), offers two paths, both closed at first and exclusive (opening one closes the other; "Vou usar no navegador", "Tenho o app Pindrel" with the QR code), with entrance motion that respects `prefers-reduced-motion` and never starts the title transparent (no first contentful paint otherwise), explains what the QR contains, and **forwards a device that already trusts the server to HTTPS** after ~2 s (`?ficar` stays; a "Ficar nesta página" link cancels). It, `/server/ca.pem` and `/server/ca.crt` answer **only to peers on the local network** (`lan_peer`: loopback, private, link-local, unique-local; 100.64/10 where Tailscale lives is not) and never through a declared proxy: from the internet they are 404. Plain language on the page ("chave de segurança"), the technical terms inside the details.
- **Plain HTTP port while TLS is on** (`HTTP_MODE=full`, the default, answers everything as if TLS were off, so a client with no HTTPS side keeps working and no certificate has to be installed anywhere; the strict mode is `HTTP_MODE=redirect`): only `/server/info/`, `/server/ca.pem`, `/server/ca.crt`, `/server/connect/` answer; a browser opening `/` gets the connection page (how to pair, how to install the certificate per OS, a live "does this device already trust the server" check); other GETs are 308-redirected to HTTPS; POST/PUT/DELETE and WebSocket get 426 (a password must not travel in clear because a client ignored a redirect). A declared proxy (`TRUSTED_PROXIES`) that ended the TLS itself is exempt. HSTS is deliberately not sent (it only works with a trusted certificate and is no protection for IP addresses).
- **Replicas** are told the scheme with `X-Forwarded-Proto` (set by the gateway; only a declared proxy may supply it); the API marks `refresh_token` as `Secure` when it is `https`. The API sets `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options` and `Permissions-Policy` on every answer and a strict `Content-Security-Policy` on the web page (`webCSP` in `router.go`).
- **WebSocket** goes through the gateway as an HTTP/1.1 upgrade (`src/websocket.rs`); a browser's `Origin` must be the server's own host or in `WS_ALLOWED_ORIGINS` (Cross-Site WebSocket Hijacking), native clients send none.
- **Planned, not built: ACME mode** (a built-in client for Let's Encrypt, DNS-01 only because a LAN cannot answer HTTP-01). For people who own a domain (or a free DDNS name): certificates every device trusts with nothing to install, and no CA key on the server. Rules decided: scoped DNS token (TXT records of one zone only, ideally the `_acme-challenge` CNAME delegated to a zone made for it), kept in a 0600 file never in env/logs; a generic "webhook" provider first (the image has no shell, so no exec hooks); fall back to the own CA when renewal fails so the server stays reachable; the app trusts the system roots for domain names and the pinned CA for IP addresses. Until then `lego` + `TLS_CERT_FILE` already works (measured: 10 to 12 MiB for ~1.3 s every ~60 days).
- **Raspberry Pi / arm64:** the gateway image is built with the `selfcert` feature by default (TLS code present, off until `TLS_AUTO`), for amd64 and arm64 from the amd64 builder with no emulation: `ring` has C and assembly parts, so the arm64 build needs a C compiler for the target, and `gateway/Dockerfile` installs `zig` (it carries the musl headers and libraries of every target) and points `CC_aarch64_unknown_linux_musl`/`AR_...` at `gateway/cross/zigcc-aarch64` and `zigar` (tested with `sh gateway/cross/test_zigcc.sh`); `--build-arg FEATURES=` builds the plain gateway. `compose.tls.yml` only sets environment and memory (no `build:`), so on a host that runs the released images it goes after `compose.registry.yml` (steps in `deploy/README.md`, "HTTPS e pareamento no Raspberry Pi").
- **Known limits:** WebSocket over HTTP/2 is refused (no browser offers it).
- **mDNS and HTTPS:** the record keeps the plain HTTP port as its port (a client that does not know HTTPS keeps working) and adds the TXT entry `tls=<port>` when the gateway has a TLS side; `DiscoveredServer.tls_port` (proto field 6, 0 = none) carries it to the web and the app, which prefer HTTPS and fall back to the plain port when there is none. The app also reads `x-pindrel-tls` from `/server/info/`, which stays the authority; a `tls` outside 1024-65535 is read as "none".
- **Security decisions:** a full security audit is postponed until the features are done (notes, vault, sync, WebSocket). `DEBUG_MODE=true` (Swagger) on the developer's machine is intentional. Pending for the audit: JWT HS256 with a shared secret and access/refresh tokens of the same kind, the CI and release chain (image signing, token scopes), the `ca.key` at rest, the DNS token scope once ACME exists.

## Backend architecture

**Wire format is Protobuf, not JSON.** Request bodies are `proto.Unmarshal`ed into types from `internal/api/dto` (generated from `shared/protos/*.proto`). Responses go out as `application/x-protobuf` through `api.WriteResponse(w, status, msg)` and `api.WriteError(w, status, code, message)` in `internal/api/response_http.go`. To add or change a payload, edit the `.proto` file, run `make proto`, and update all three clients. The hand-written structs in `internal/auth/dto.go` are legacy (there is a TODO to remove them). Only `LoginResult` there is still used.

Request flow: `cmd/api/main.go` wires everything (config → pgx pool → `db.New(pool)` → service → handler). `internal/api/route/router.go` builds the chi router.

- Per domain package (`internal/auth`, and `internal/vault`, which is still empty stubs): `handler.go` (HTTP, proto decode/encode, maps sentinel errors to status codes and error-code strings) → `service.go` (business logic, returns `Err*` sentinel errors) → sqlc `*db.Queries` as the repository. No separate repository layer exists for auth.
- Input validation lives in `internal/validator` (ozzo-validation, operating on proto dto types). Handlers call it before the service.
- DB access: write SQL in `internal/database/queries/*.sql` with sqlc annotations, then run `sqlc generate`. Never edit `internal/database/db/` by hand. UUID columns map to `github.com/google/uuid.UUID`.
- mDNS is **not done by the Go API**; the Rust `gateway/` does it (`gateway/src/discovery.rs`, crate `mdns-sd`): it announces `_pindrel._tcp` named `SERVER_NAME` on the LAN interface only (the one holding the default route; `MDNS_INTERFACES` overrides), resolves name conflicts by renaming (`Pindrel (2)`; avahi renames to `Pindrel #2`), says goodbye on shutdown and keeps a live list of the other servers (itself hidden) served as protobuf `DiscoveredServers` at `GET /server/discover/` (the browser has no mDNS). The only Go piece is `GET /server/info/` (`internal/server`: `ServerInfo` with name and `registration_enabled`, built once at startup, so changing them needs a restart). mDNS only works on the host network: a bridge container cannot see the LAN, and Docker Desktop (Windows/macOS) runs containers in a VM, so there the gateway must run as a native binary pointing `UPSTREAMS` at published `localhost` ports (not tested). A second avahi on the same machine is fine for the gateway (tested: avahi renamed itself), unlike a second avahi, which loops on hostname conflicts. Verified on a real Raspberry Pi 4 (Debian 13, aarch64, avahi-daemon active) from another machine on the LAN: API replicas + gateway + Postgres worked (register 0.27 s / login 0.21 s with Argon2 on the Pi, gateway 1.6 MB RSS, API ~60 MB RSS each), and each side discovered the other. Multicast over Wi-Fi is lossy (measured 21-48% loss between two Wi-Fi machines on 2.4 GHz at -60 dBm; Wi-Fi power save was off on both), and the library resends its browse query with a delay that doubles up to an hour, so discovery used to take up to about a minute. The gateway therefore restarts the search every `MDNS_REFRESH_SECS` while it knows no other server (4x that once it does): calling `browse` again replaces the receiver, restarts the backoff at 1 s and replays the cache (`discovery::browse_loop`). A/B on the PC<->Pi pair, 4 trials each: discovery took about 1 s in most trials either way; the one bad trial without the restart took 63 s on both sides, the one slow trial with it recovered after 16 s (small sample, and the network was mostly good in that window). The gateway also remembers the servers it has seen (`gateway/src/known.rs`): one that stops being announced (a lost refresh on Wi-Fi, or a goodbye) is not dropped but checked with a plain TCP connection to its last addresses, right away and every `KNOWN_PROBE_SECS`, and stays listed while it answers and is forgotten when it does not; with `KNOWN_SERVERS_FILE` the memory is saved (atomically, as a protobuf `DiscoveredServers`) and loaded at start so a restarted gateway lists the others at once (verified on the Pi with mDNS off on both sides). Security: announcements are untrusted, so the gateway only connects to addresses in its own subnet (`Lan::allows`, from the interface netmask; never itself, loopback, another network or the internet) and ports from 1024, otherwise a device on the LAN could use it as a port scanner and read the result in `/server/discover/`; both tables are capped (256 announced, 64 remembered) and the file is parsed strictly (never panics). On shutdown the port is closed *before* the mDNS goodbye, so the others do not find it still open. Each gateway has a stable random id (`gateway/src/identity.rs`, kept in `SERVER_ID_FILE`, a volume in `compose.lb.yml`; without the file a new one per start): it goes in the TXT record (`id=`), in `DiscoveredServer.id` (proto field 5), in the `x-pindrel-id` header of `GET /server/info/` (a tunnel gets it too, it is not private) and hides the gateway from its own list. The web (`web/src/lib/stores/trust.ts`, `localStorage`) and the mobile (`features/auth/data/server_trust.dart`, secure storage) remember the id of every server they opened by name; when the same name answers with another id (or none where there was one) they ask for confirmation (`Este servidor mudou`: it does not block) and the mobile never picks such a server on its own at start. Set `GOMEMLIMIT` below the RAM ceiling.
- Config: `internal/config/config.go` parses env vars with a generic `parseEnv` that collects every error before failing. A `nil` fallback means the variable is required. Add new settings there and to `backend/.env.example` and `compose.yml`.

Auth model:
- JWT HS256 (`internal/auth/jwt.go`) with a `user_id` claim and a random `jti`. Access and refresh tokens are the same kind of token with different expiries.
- The access token goes in the response body. The refresh token goes in an `HttpOnly` `refresh_token` cookie.
- Logout revokes tokens by inserting the `jti` into `revoked_tokens`. `ValidateToken` checks that table on every call.
- `middleware.AuthMiddleware` puts the user's UUID into the context under `pkg/context.UserIDKey`. Protected routes go inside the `r.Group(...)` in `router.go`.
- Passwords are hashed with Argon2id (`internal/auth/password.go`). A common-password blocklist is embedded from `internal/auth/data/` as a byte-sorted, trimmed file searched in place with a binary search (`inSortedLines`; a map of it cost ~4 MiB of heap; keep the file sorted with `LC_ALL=C sort -u`, a test checks it). Each Argon2 run keeps ~19 MiB alive, so only 2 run at once per instance (`SetArgonLimits`); the others wait up to 5 s and then get `503 server_busy` + `Retry-After`. Measured before the cap: 16 simultaneous logins = 330 MiB RSS, 64 = 1 GiB; `GOMEMLIMIT` does not help because the memory is live. Login also verifies a dummy hash when the e-mail does not exist, so response time does not reveal which accounts exist. Request bodies of `/auth/login/` and `/auth/register/` are capped at 16 KiB (413 `payload_too_large`).

Router details:
- Routes are registered **with trailing slashes** (`/auth/login/`).
- **Who a request belongs to (in-app limits).** `internal/clientip` (built on `realclientip-go`, configured by `TRUSTED_PROXIES` and `CLIENT_IP_HEADER`, same rules and names as the gateway): the connection's address, unless that address is a listed proxy, and then only the one configured header, read from the right. The library's strategies ignore who connected, so `Resolver.Key` checks the peer itself; headers over 2 KiB are ignored; IPv6 counts as its /64. Before this the global limit read the LEFTMOST `X-Forwarded-For` of any private/loopback peer, which the client writes, so it could be dodged (130 requests with 130 different values all passed); `TestRouter_GlobalLimitCannotBeDodgedWithForwardedFor` is that experiment. `config.Config.ClientKey` carries it (nil = the connection's address).
- Login and register each have their own per-IP token-bucket limiter (`internal/middleware/ratelimit.go`, cleaned up by a goroutine in `main.go`). A global `httprate` limit of 100 requests per minute also applies.
- Swagger UI (`/swagger/*`) is mounted only when `DEBUG_MODE=true` **and** the binary is built with `-tags swagger` (`go run -tags swagger ./cmd/api`; Docker: `GO_TAGS=swagger`): its package copies ~35 MB of UI files into the heap when imported (~9 MiB live), so the release image leaves it out. The swag `@Router` annotations in `internal/auth/handler.go` match the router (no `/api` prefix, trailing slashes), and `backend/docs/` has been regenerated to stay in sync.

Known gaps in the current code:
- CORS origins are hardcoded in `router.go`; there is no `ALLOWED_ORIGINS` setting.
- The web build in `./public` is served by `spaHandler` in `router.go` (`GET`/`HEAD /*`, registered after the API routes) with an **allowlist**, no blocklist, in three steps: (1) the path is a real file inside `./public` → serve it; (2) otherwise `isWebRoute(path)` is true → serve `index.html`; (3) anything else (`/api/auth/login/`, `/auth/nope/`, `/random`) → 404. Files under `/assets/` (named by content hash) go out with `Cache-Control: immutable` and, when the client accepts it, as the `.br`/`.gz` sibling that `web/vite.assets.ts` writes at build time (the server compresses nothing at request time: no CPU or RAM, only disk; `servePrecompressed`, stale or range requests fall back to the plain file); the same plugin puts the stylesheet inside `index.html` (one request less before the first paint) and the logo scenes are a lazy chunk (`LogoMark`). Measured with Lighthouse, mobile 3G profile, real instance: LCP 1.8 s to 1.2 s, 185 KiB to 41 KiB. `isWebRoute` currently allows `/`, `/login` and `/notes/:id` (one segment). **The web has no router yet**: `App.svelte` renders `routes/Login.svelte` (implemented, with tests) for every path, and `Dashboard`/`NotePage` in `web/src/routes/` are still empty placeholders. When you add or rename a web page route, update `isWebRoute` and its test (`internal/api/route/static_test.go`) in the same change. The API lives at the server root (no `/api` prefix) and the web calls it with relative paths (`/auth/...`). There is no `VITE_API_URL`, no `web/.env` and no `web/.env.example`; in dev, `web/vite.config.ts` proxies the API prefixes to `localhost:8080`.
- Email validation uses `is.EmailFormat` (syntax only, no DNS lookup).
- The `notes` table exists in the schema, but no queries or handlers use it yet. Blocks live inside `notes.content` (JSONB); there are no `pages`/`blocks` tables. Planned note and vault access goes through a single bulk endpoint, `POST /sync/bulk/`, built on `DocumentSyncRequest`/`DocumentSyncResponse` in the proto (revision-based conflict detection), not per-resource routes. Blocks are a flat list (no `children` yet), tags will be a `TEXT[]` column on `notes`, sharing is planned, and user settings live only on the device, never in Postgres.

## Conventions

- **Branches `main` and `dev` differ on purpose in four files; check before every merge.** `main` is the release branch: it keeps the release stub of the debug theme override (`web/src/lib/logo/debug.ts`, and no `debug.test.ts`) and requires `DB_PASSWORD` and `JWT_SECRET` in `compose.yml`/`.env.example` with no defaults; `dev` keeps the full override and the `change_me` defaults, in ONE commit of its own on top of what `main` has (`chore(dev): keep the debug theme override...`). Only `debug.ts` is protected by `.gitattributes` (`merge=ours`, needs `git config merge.ours.driver true` in each clone) and only when BOTH sides changed it; `compose.yml`, `.env.example` and `debug.test.ts` are not, so a careless `git merge dev` can put the `change_me` defaults in a release (it happened in a rehearsal, with zero conflicts). Before merging `dev` into `main`: `git merge --no-commit --no-ff dev && git diff --cached --stat`; none of those four files may be listed, otherwise `git merge --abort`. If `dev` is rebuilt, or gets a commit that does not come from `main`, anchor it once with `git merge -s ours dev` on `main` (no file changes, `dev` becomes an ancestor; done at `bff4a4b`) and only then merge normally. A branch that starts from `main` (a fix branch) must not be fast-forwarded into a `dev` that is behind `main`: it brings the stub along; `dev` has to contain `main` first. Never rewrite `main`; `dev` is local until the user pushes it.
- **Tests are mandatory.** Every component or service created (Go, Rust, Web or Flutter) must ship with automated tests written together with the implementation, not afterwards.
- **Stress the system (concurrency and robustness tests).** When writing tests, also write concurrency and robustness tests wherever they apply, and try to break the system by every means: heavy load (floods of requests or connections, many source addresses, huge bodies, slow or never-finished requests, resource exhaustion), malformed or unexpected input, spoofed headers, injection. If something breaks, fix the code; do not weaken the test.
- **Break it like a confused person (careless-use tests).** Also write tests as if you were an elderly person or just a very random one, and try to break it that way too: wrong or repeated taps and clicks, doing things in an odd order, leaving halfway, empty, huge or strange text, stray spaces, a screen that is too small or too crowded, a bad connection. If something breaks, fix it.
- **Code comments are in English** (Go, Rust, Dart, TS/Svelte, YAML, Dockerfiles, shell, Python), because it is the more universal language. Write them only where the code does not explain itself (the *why*, an invariant, a measured number, a non-obvious constraint); do not narrate what the next line does or restate a name. User-facing text (UI strings, e-mails) and log/error messages are not comments: they stay in Portuguese where they already are, so match the surrounding code. Generated files, tool directives (`//go:build`, `# syntax=`, swag annotations, sqlc `-- name:`) and quoted test names stay as they are. Markdown docs (`.forgejo/README.md`, `deploy/README.md`) are prose, not code comments, and stay in Portuguese.
- **Go tests that need the real database are named `TestDB_*`** (e.g. `TestDB_Service_Register_DuplicateEmail`, `TestDB_Pool_...`). Anything that loads `backend/.env` (`godotenv.Load`) or opens a connection (`database.NewConnection`, `pgxpool.*`), directly or through a helper, must carry the prefix. Why: the CI runner (Raspberry Pi) has no Postgres and no `.env`, so `.forgejo/workflows/backend.yml` skips exactly `^TestDB_` (`go test ./... -skip '^TestDB_'`); a database test with another name passes locally and breaks the pipeline. Before this convention the workflow kept a list of name prefixes that people forgot to update. `internal/testnaming` enforces it: it parses every `_test.go`, follows helper calls inside a directory, and fails with the names to rename. `go test ./... -run TestDB_` runs only the database tests, `-skip TestDB_` only the ones that run without it (what the CI runs). `config.Load` alone does not count (the config tests set variables with `t.Setenv`).
- Go tests use external test packages (`package auth_test`) and compare protobuf messages with `go-cmp` + `protocmp`.
